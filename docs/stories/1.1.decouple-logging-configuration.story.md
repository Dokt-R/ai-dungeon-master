# Story 2.1: Decouple Logging Configuration

## Status

Done

## Story

**As a** developer,
**I want** the logging configuration to be managed by the application entry point, not a shared module,
**so that** I can have predictable and environment-specific logging behavior without side effects.

## Acceptance Criteria

1. [x] The `logging.basicConfig()` call is completely removed from `packages/shared/error_handler.py`.
2. [x] The `error_handler.py` module retrieves its logger using `logging.getLogger(__name__)`.
3. [x] The FastAPI application (`packages/backend/main.py`) initializes the logging configuration for the backend service.
4. [x] The Discord bot application (`packages/bot/main.py`) initializes the logging configuration for the bot service.
5. [x] Existing logging functionality continues to work as expected in both the backend and the bot.

### Implementation Guidance

1. In `packages/shared/error_handler.py`:
   - Remove lines that configure logging (likely lines 6-9 based on previous analysis)
   - Add `logger = logging.getLogger(__name__)` at the module level
   - Replace any direct `logging.error(...)` calls with `logger.error(...)`

2. In `packages/backend/main.py`:
   - Add logging configuration at the beginning of the file, before the FastAPI app is created
   - Example configuration:
     ```python
     import logging
     logging.basicConfig(
         level=logging.INFO,
         format="%(asctime)s - %(name)s - %(levelname)s - %(message)s"
     )
     ```

3. In `packages/bot/main.py`:
   - Add the same logging configuration as in the backend's main.py
   - Place it at the beginning of the file, before the bot client is created

### Testing Standards

- **Test file location**: This is a configuration change, so tests would primarily be in integration tests
- **Test standards**: 
  - Ensure that after the change, log messages still appear in the console with the correct format
  - Verify that log messages show the correct module name (e.g., `packages.shared.error_handler`)
- **Testing frameworks and patterns to use**:
  - Manual testing by running the applications and triggering error conditions
  - Integration tests in `tests/integration/` that verify logging behavior if they exist
- **Specific testing requirements for this story**:
  - Confirm that removing the centralized configuration doesn't break existing logging
  - Verify that each application's entry point now controls its own logging configuration
